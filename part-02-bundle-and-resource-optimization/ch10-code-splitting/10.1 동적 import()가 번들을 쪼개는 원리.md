# 개요

불필요한 폴리필을 제거하고 사용하지 않는 라이브러리를 삭제했는데도 초기 번들 크기가 여전히 크다면, 많은 개발자가 이 단계에서 코드 스플리팅을 도입함 → 하지만 실제로 사용자 경험을 측정해보면 기대만큼의 성능 개선이 나타나지 않거나 오히려 로딩이 더 느려지는 경우도 있음

문제는 많은 개발자가 코드 스플리팅을 단순히 ‘문법’이나 ‘기능’으로만 이해하고 적용하기 때문.

import()를 어디에 넣으면 번들이 쪼개진다는 것은 알지만, 전략이 없다면 효과는 제한적임.

잘못된 코드 스플리팅은 오히려 성능을 해칠 수 있음

### 의문

Next.js, 넉스트, 리믹스 같은 현대 프레임워크는 이미 자동 코드 스플리팅을 제공함

굳이 동적 import()의 원리나 청크 최적화 전략을 알아야 할까?

### 이유 3가지

1. 프레임워크의 기본 설정이 모든 상황에 최적은 아님
   - 프레임워크는 라우트 단위로 분할할 뿐, 라우트 내부의 조건부 로딩까지 자동으로 최적화하지는 않음
2. 문제가 생겼을 때 디버깅할 수 있어야 함
   - 번들러가 청크를 어떻게 구성하는지 알아야 함
3. 프레임워크의 한계를 넘어선 최적화가 필요할 때가 있음
   - 프레임워크는 합리적인 기본값을 제공하지만, 최적의 성능을 위해서는 결국 내부 동작을 이해하고 직접 조정해야함

### 효과적인 코드 스플리팅은 2가지를 이해하는 것에서 시작

1. 사용자의 행동 패턴
2. 애플리케이션의 구조

# 10.1 동적 import()가 번들을 쪼개는 원리

import() → 번들러에게 ‘이 지점에서 번들을 분할하라’는 명령

정적 import() 동적 import()의 큰 차이 : ‘언제 의존성이 해결되는가’

- 정적 import() : 빌드 타임에 모든 의존성을 분석해서 하나의 번들로 묶음
- 동적 import() : 런타임까지 의존성 해결을 지연시킴

## 정적 import() vs 동적 import()의 차이

### 정적 import

파일 최상단에 import문을 선언하면 빌드 타임에 모든 의존성이 분석되고 하나의 번들 파일로 묶임

```jsx
import React from "react";
import { Header } from "./components/Header";
import { Footer } from "./components/Footer";
import { formatDate } from "./utils/dateUtils";

function App() {
  return (
    <div>
      <Header />
      <main>Content</main>
      <Footer />
    </div>
  );
}
```

웹팩으로 빌드 → React, Header, Footer, formatDate 모두가 app.js 하나로 묶임

→ 사용자가 페이지를 처음 로드할 때 이 모든 코드를 다운로드하고 파싱하고 실행해야 함

### 동적 import

Promise를 반환하는 함수

빌드 타임에는 ‘이 지점에서 번들을 분할한다’는 정보만 기록하고, 실제 모듈 로딩은 런타임에 일어남

```jsx
import React from "react";
import { Header } from "./components/Header";

function App() {
  const [showDashboard, setShowDashboard] = React.useState(false);
  const [Dashboard, setDashboard] = React.useState(null);

  const loadDashboard = async () => {
    // 사용자가 버튼을 클릭할 때만 Dashboard 로드
    const module = await import("./components/Dashboard");
    setDashboard(() => module.default);
    setShowDashboard(true);
  };
  return (
    <div>
      <Header />
      <button onClick={loadDashboard}>
        대시보드 열기
        {showDashboard && Dashboard && <Dashboard />}
      </button>
    </div>
  );
}
```

빌드 → Dashboard 컴포넌트와 그 의존성들이 별도의 청크 파일 (ex. Dashboard.chunk.js)로 분리됨

사용자가 버튼을 클릭하기 전까지는 이 청크를 다운로드하지 않음

- 청크(chunk) : 번들러가 JavaScript 코드를 나눠 만든 작은 파일 조각

### 코드 스플리팅 결정시 고려할 것

- 사용 빈도 : 차트를 보는 사용자가 10% → 코드 스플리팅 효과적
- 사용 시점 : 페이지 로드 직후 바로 필요한 기능이라면 쪼개지 않는 것이 나음 → 로딩 지연이 사용자 경험을 해침
- 리소스 크기 : 10KB 정도의 작은 모듈은 쪼개지 않는 것이 나음 → HTTP 요청 오버헤드가 더 클 수 있음
- 네트워크 환경 : 느린 네트워크 환경의 사용자가 많다면 초기 번들을 최소화하는 것이 더 중요함

## 번들러가 청크를 생성하는 방식

### Q. 번들러는 정확히 어떤 기준으로 청크를 만들고, 어떻게 이름을 지정하며, 청크 간 의존성은 어떻게 관리할까?

Ex. 비트의 빌드 과정

비트는 내부적으로 롤업을 사용하여 프로덕션 번들을 생성함

1. 진입점 분석 : indexl.html에서 시작하여 <script type=’module’>태그를 찾음
2. 의존성 그래프 생성 : 모든 import 문을 따라가며 의존성 트리를 만듦
3. 청크 분할 지점 식별 : 동적 import()를 만날 때마다 ‘분할 지점’으로 표시함
4. 청크 생성 : 분할 지점을 기준으로 코드를 여러 청크로 나눔
5. 청크 최적화 : 롤업의 트리 셰이킹을 통해 사용하지 않는 코드를 제거함
6. 청크 이름 저장 : 각 청크에 해시가 포함된 고유한 이름을 부여함

```jsx
manualChunks: undefined;
```

벤더 청크를 수동으로 분리하지 않는 기본 상태

→ 모두 하나의 파일로 묶임

!image.png

```jsx
manualChunks : {
	‘vendoer-react’ : [’react’, ‘react-dom’],
}
```

manaulChunks는 번들러에게 지시함

“react와 react-dom은 vendoer-react라는 별도 파일로 묶어줘”

!image.png

비트가 청크를 생성한 전략

1. 동적 import() 청크 분리 : App.jsx에서 import(’./ChartComponent’)를 만나면, ChartComponent.jsx와 그 의존성(Chart.js)을 별도 청크로 분리함
2. 벤더 청크 생성 : manualChunks 설정에 따라 react와 react-dom을 vender-react 청크로 묶음
3. 메인 청크 최소화 : 초기 로드에 필요한 최소한의 애플리케이션 코드만 index.js에 남김

청크 파일에 포함된 해시는 파일 내용을 기반으로 생성됨

파일 내용이 변경되면 해시도 변경되므로, 브라우저 캐싱과 함께 사용하면 변경되지 않은 청크는 캐시에서 바로 로드할 수 있음

### Q. 여러 동적 청크에서 공통으로 사용하는 모듈이 있다면 어떻게 될까?

ex.) `Dashboard`와 `Settings`가 모두 `api.js`를 사용하는 경우

```
// App.jsx
const Dashboard = () => import("./Dashboard");
const Settings = () => import("./Settings");
```

```
// Dashboard.jsx
import { fetchData } from "./api/";
import Chart from "chart.js";
```

```
// Settings.jsx
import { fetchData } from "./api/";
```

비트는 기본적으로 공통 모듈을 자동으로 감지하고 별도 청크로 분리함

#### Vite와 Rollup의 역할

Vite는 내부적으로 Rollup을 사용해 프로덕션 빌드를 처리함

Rollup은 기본적으로 다음을 자동으로 처리함

- 여러 동적 청크에서 공통으로 사용하는 모듈 탐지
- 공통 모듈을 별도 청크로 분리
- 각 동적 청크에서 공통 청크를 참조하도록 구성
- 중복 코드 제거

따라서 일반적인 경우에는 공통 모듈을 직접 분리하지 않아도 됨

이를 더 세밀하게 제어하려면 manualChunks함수를 사용

#### `manualChunks`를 사용하는 경우

공통 모듈을 번들러가 자동으로 나누도록 맡길 수도 있지만 청크 이름과 구성을 직접 지정할 수도 있음

```jsx
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          "vendor-react": ["react", "react-dom"],
          "vendor-charts": ["chart.js", "react-chartjs-2"],
          "vendor-utils": ["lodash-es", "date-fns"],
        },
      },
    },
  },
};
```

- 이점
  - 리액트는 거의 변경되지 않으므로 vendor-react 청크는 오랜 기간 캐시될 수 있음
  - Chart.js를 업데이트하면 vendor-charts만 새로 다운로드하면 되고 리액트 청크는 캐시에서 그대로 사용할 수 있음

### Q. 번들러가 생성한 청크는 런타임에 어떻게 로드될까?

비트는 개발 환경과 프로덕션 환경에서 다르게 동작함

- 번들러 : 여러 JS 파일을 묶어서 브라우저가 받기 좋은 형태로 만들어 주는 도구 (비트, 웹팩, 롤업)
  - 번들링 : 여러 개의 JavaScript 파일과 라이브러리를 브라우저가 실행할 수 있는 파일로 묶는 과정
- 청크(chunk) : 번들을 나눈 조각 파일 하나하나
- 동적 import() : 필요해지는 순간에 파일을 불러오는 문법
  ```jsx
  import Chart from "./ChartComponent"; // 정적 import: 페이지가 열릴 때 무조건 불러옴
  const module = await import("./ChartComponent"); // 동적 import: 이 줄이 실행될 때 불러옴
  ```

#### 개발 환경(npm run dev) : 묶지 않는다

개발 환경에서 비트는 번들링을 하지 않음 → ESModule을 네이티브로 제공하므로 브라우저가 직접 파일을 요청함

#### 프로덕션 환경(npm run build) : 롤업으로 제대로 묶는다

실제 사용자에게 배포할 때는 최적화가 중요하므로 비트가 롤업이라는 도구로 번들을 만듦

과정

1. 의존성 그래프 분석 : index.html부터 시작해서 모든 import 문을 따라가며 의존성 트리를 구성함
2. 청크 분할 지점 식별 : 동적 import(./ChartComponent’)를 만나면 이 지점을 청크 경계로 표시함
3. 코드 변환 및 최적화 : JSX를 JS로 변환하고 트리 셰이킹으로 사용하지 않는 코드를 제거하며 코드를 압축(minify)함

   Q. 왜 JSX를 JS로 변환하지?
   1. JSX는 자바스크립트가 아니다
      - 브라우저가 JSX를 읽지 못함. 브라우저가 실행할 수 있는 건 순수한 자바스크립트뿐.

4. 청크 생성 및 해시 추가 : 각 청크를 별도 파일로 생성하고 내용 기반 해시를 파일명에 추가함
5. 경로 재작성 : 상대 경로(./ChartComponent)를 실제 빌드된 파일 경로(/assets/ChartComponent-BLNUy8Dt.js)로 변경함

⇒ 빌드가 끝나면 코드가 이렇게 바뀜

```jsx
// 전: 내가 쓴 코드
await import("./ChartComponent");
// 후: 빌드 결과
await import("/assets/ChartComponent-BLNUy8Dt.js");
```

#### 파일 이름 뒤의 `BLNUy8Dt`

파일 내용으로 계산한 해시 → 이걸 붙이는 이유는 브라우저 캐시 때문

- 브라우저는 한 번 받은 파일을 저장해 두고(캐시) 재방문 때 다시 쓰려고 함.
- 코드를 수정하면 내용이 바뀌니 해시도 바뀌고, 파일 이름이 `ChartComponent-Xk92aQ.js`처럼 변경됨. 브라우저는 처음 보는 이름이니 새로 다운로드함.
- 코드를 안 고쳤다면 이름이 그대로라 캐시된 파일을 재사용함. 다운로드가 필요 없으니 빠름.

해시가 없으면 → 코드를 고쳐 배포해도 사용자가 옛날 파일을 계속 보는 문제 발생

## React.lazy()와 서스펜스의 동작 원리

동적 import()를 직접 사용하는것도 가능하지만, 대부분의 프레임워크는 더 편리한 추상화 제공 → **lazy(), Suspense**

### React.lazy()

동적 import()를 감싸는 래퍼(wrapper) 함수 → 컴포넌트를 Promise로 반환하는 함수를 받아서 리액트가 이해할 수 있는 형태로 변환함

```jsx
const Dashboard = lazy(() => import("./Dashboard"));
```

내부 구현을 단순화해서 보여줌

```jsx
// React.lazy()의 단순화된 구현
function lazy(loadComponent) {
  let status = "pending";
  let result;
  let promise = loadComponent().then(
    (module) => {
      status = "success";
      result = module.default;
    },
    (error) => {
      status = "error";
      result = error;
    },
  );

  return function LazyComponent(props) {
    if (status === "pending") {
      // 컴포넌트가 아직 로드되지 않음 - Promise를 throw
      throw promise;
    }
    if (status === "error") {
      // 로딩 실패 - 에러를 throw
      throw result;
    }
    if (status === "success") {
      // 로딩 성공 - 컴포넌트 렌더링
      const Component = result;
      return <Component {...props} />;
    }
  };
}
```

#### 핵심 : Promise를 throw한다

일반적으로 throw는 에러를 던질 때 사용 ↔ 리액트는 Promise도 catch할 수 있음

Suspense 컴포넌트는 하위 컴포넌트가 Promise를 throw하면 이를 잡아서 로딩 상태를 관리함

#### 기타 개념

### Suspense

파일을 받는 동안 보여줄 대체 화면을 정해 두는 안전망

⇒ 둘을 같이 써야 코드 스플리팅이 화면에서 자연스럽게 동작함

#### fallback : 대비책, 임시 대안

suspense에서는 진짜 화면이 준비될 때까지 대신 보여줄 화면을 뜻함

```jsx
<Suspense fallback={<div>로딩 중...</div>}>
  <Dashboard />
</Suspense>
```

#### fallback이 없으면?

Suspense로 감싸지 않으면, lazy 컴포넌트가 "아직 준비 안 됐어"(Promise)를 던져도 받아 줄 곳이 없음 → 에러 발생!!

⇒ lazy를 쓸 때 `Suspense`와 fallback이 짝으로 따라다니는 이유

#### Promise : 비동기 작업의 결과를 나중에 받을 수 있도록 표현하는 객체

ex.) 서버에서 데이터를 가져오는 상황

```jsx
const promise = fetch("/api/users");
```

fetch()는 서버에 요청을 보내지만 서버의 응답이 언제 도착할지는 알 수 없음 → 응답 데이터를 즉시 반환하는 대신 Promise를 반환함

- 3가지 상태
  - pending : 작업 진행 중
  - fulfilled : 작업 성공
  - rejected : 작업 실패

#### .then() : Promise가 성공적으로 완료되었을 때 실행할 함수를 등록하는 메서드

```jsx
fetch("/api/users").then((response) => {
  console.log("서버 응답 도착!");
});
```

- 순서
  1. fetch()가 서버에 요청을 보냄
  2. Promise가 pending상태가 됨
  3. 서버 응답을 기다리는 동안 다른 코드가 실행될 수 있음
  4. Promise가 성공적으로 완료되면 .then()의 콜백이 실행됨

#### throw : 현재 실행 흐름을 중단하고 값을 던지는 문법

- 보통은 오류를 던질 때 사용함
- throw Promise는 왜 사용할까?
  - React가 화면을 렌더링하는 도중 아직 준비되지 않은 컴포넌트를 만났다고 가정
    ```jsx
    const Dashboard = lazy(() => import("./Dashboard"));
    ```
    `Dashboard` 컴포넌트는 동적 import로 불러오기 때문에, 처음에는 파일 다운로드가 끝나지 않았을 수 있어요.
    이때 React에게 다음과 같은 상황을 전달해야 해요.
    > Dashboard를 아직 렌더링할 수 없어요. 로딩이 완료될 때까지 다른 화면을 보여주세요.
    React의 지연 로딩과 Suspense 메커니즘에서는 이 상황을 처리하기 위해 Promise와 유사한 대기 객체를 던지는 방식을 사용해요.
    ```jsx
    throw promise;
    ```
    이것은 `await promise`와는 달라요.
    - `await promise`: 현재 비동기 함수의 진행을 일시적으로 기다려요.
    - `throw promise`: 현재 실행을 중단하고 Promise를 바깥으로 던져요.
    React가 렌더링 중 던져진 Promise를 인식하면, 가까운 `Suspense` 경계에서 로딩 UI를 표시하고 작업이 끝난 뒤 렌더링을 다시 시도할 수 있어요.
    !image.png
    즉, `throw promise`는 이 문맥에서 오류가 발생했다는 뜻이 아니라, 렌더링에 필요한 작업이 아직 완료되지 않았다는 신호로 이해하면 돼요.

### 지연 로딩 컴포넌트의 제약사항 3가지

1. 지연 로딩 컴포넌트는 반드시 default export여야 한다.

   ```jsx
   // Dashboard.js에서 명명 엑스포트 사용
   export funciton Dashboard() {
   	return <div>Dashboard</div>
   }

   // lazy()에서 사용 시 변환 필요
   const Dashboard = lazy(() =>
   	import('./Dashboard').then((module) => ({
   		default: module.Dashboard,
   	})),
   )
   ```

2. 지연 로딩 컴포넌트는 반드시 서스펜스 경계 안에 있어야 한다.

   Suspense없이 지연 로딩 컴포넌트를 사용하면 Promise를 catch할 곳이 없어 에러 발생

   ```jsx
   // 에러 발생 - Suspense 없음
   function App() {
   	const Dashboard = lazy(() => import('./Dashboard'))
   	return <Dashboard />
   }

   // 정상 동작 - Suspense로 감쌈
   function App() {
   	const Dashboard = lazy(() => import('./Dashboard'))
   	return (
   		<Suspense fallback{<div>로딩 중...</div>}>
   			<Dashboard />
   		</Suspense>
   	)
   }
   ```

3. 여러 지연 로딩 컴포넌트를 하나의 서스펜스로 감쌀 수 있다.

   ```jsx
   function App() {
   	const Dashboard = lazy(() => import('./Dashboard'))
   	const Settings = lazy(() => import('./Settings'))

   	return (
   		<Suspense fallback{<div>로딩 중...</div>}>
   			<Dashboard />
   			<Settings />
   		</Suspense>
   	)
   }
   ```

   사용자가 페이지에 처음 접속할 때 Dashboard와 Settings를 동시에 로드하면
   → 두 청크가 병렬로 다운로드되고, 둘 다 완료될 때까지 fallback이 표시됨

### Suspense 세 가지 패턴

#### 패턴 1 : 단일 서스펜스

```jsx
// 모든 컴포넌트를 하나의 서스펜스로 감싸기
<Suspense fallback={<div>로딩 중...</div>}>
  {currentView === "home" && <home />}
  {currentView === "dashboard" && <Dashboard />}
  {currentView === "settings" && <Settings />}
</Suspense>
```

- 동작 : 어떤 지연 로딩 컴포넌트라도 로딩 중이면 ‘로딩 중…’ 메시지가 표시됨.
- 장점 : 코드가 간단하고 일관된 로딩 경험 제공
- 단점 : 작은 컴포넌트도 로딩 중일 때 전체 영역이 폴백으로 대체되어 깜빡임이 느껴질 수 있음

#### 패턴 2 : 독립적 서스펜스

```jsx
// 각 컴포넌트를 독립적인 서스펜스로 감싸기
{
  currentView === "dashboard" && (
    <Suspense fallback={<div>대시보드 로딩 중...</div>}>
      <Dashboard />
    </Suspense>
  );
}
{
  currentView === "settings" && (
    <Suspense fallback={<div>설정 로딩 중...</div>}>
      <Settings />
    </Suspense>
  );
}
```

- 동작 : 각 컴포넌트가 독립적으로 로딩 상태를 관리함.
- 장점 : 각 영역이 독립적으로 로드 → 일부 영역은 콘텐츠를 보여주고 일부만 로딩 중일 수 있음. ⇒ 사용자 경험이 더 세밀함
- 단점 : 코드가 복잡해지고 서스펜스 경계를 어디에 둘지 고민해야 함

#### 패턴 3 : ErrorBoundary와 함께

```jsx
// 에러 처리를 추가한 패턴
<ErrorBoundary fallback={<div>로딩 실패</div>}>
  <Suspense fallback={<div>로딩 중...</div>}>
    {currentView === "dashboard" && <Dashboard />}
  </Suspense>
</ErrorBoundary>
```

- 동작 : 청크 로딩이 실패하면(네트워크 오류, 404 등) ErrorBoundary가 에러를 포착해서 폴백을 보여줌
- 장점 : 프로덕션 환경에서 청크 로딩 실패를 우아하게 처리할 수 있음 CDN 장애나 배포 중 발생하는 문제에 대응할 수 있음
- 단점 : ErrorBoundary를 직접 구현하거나 라이브러리를 사용해야 함
