# 10.2 전략적 분할 지점 찾기

## 개요

‘어디서’ 코드를 분할해야 하는지 결정해야 함

효과적인 분할 지점 : 애플리케이션의 구조와 사용자의 행동 패턴에서 나옴

- 가장 보편적인 전략 : 라우트 기반 분할
- 컴포넌트 레벨 분할
  - 모달, 탭, 차트처럼 사용자가 명시적으로 요청했을 때만 표시되는 무거운 컴포넌트를 분할함
- 조건부 기능
  - 관리자만 접근하는 기능, 특정 사용자 그룹에만 제공되는 기능, A/B 테스트로 일부에만 노출되는 기능은 필요한 사용자에게만 로드

주의점

- 10KB 미만의 작은 모듈을 분할하면 HTTP 요청 오버헤드가 코드 크기보다 클 수 있음
- 여러 라우트에서 공통으로 사용하는 유틸리티를 각각 분할하면 중복 다운로드 발생
- 첫 화면 렌더링에 필수적인 컴포넌트를 지연 로딩시 사용자는 빈 화면을 보게됨

## 라우트 기반 코드 스플리팅

- 사용자가 특정 페이지를 방문할 때만 필요한 코드를 로드함
- 초기 로드를 하고 사용자가 페이지를 방문하면 그 페이지에 대한 청크를 추가로 로드함

### Next.js에서는?

Next.js는 파일 시스템 기반 라우팅 사용 → 별도 설정 없이 자동으로 페이지 단위 코드 스플리팅 수행

다만, 페이지 내부의 컴포넌트는 자동 분할되지 않음 → next/dynamic 사용

```jsx
// page/dashboard.js
import dynamic from 'next/dynamic'

const Chart = dynamic(() => import('..components/Chart'), {
	loading: () => <div>차트 로딩 중...</div>
	ssr: false, // 서버 사이드 렌더링 비활성화(클라이언트에서만 로드)
})

export default function Dashboard() {
	return (
		<div>
			<h1>대시보드</h1>
			<Chart />
		</div>
	)
}
```

- `ssr: false`
  - Next.js에서 Chart 컴포넌트를 서버에서 렌더링하지 않겠다는 뜻
  - 즉, Chart는 브라우저에서 렌더링됨

#### 파일 시스템 기반 라우팅이란?

파일이나 폴더 구조에 따라 URL주소가 자동으로 만들어지는 방식

#### 서버 사이드 렌더링(SSR, Server-Side Rendering) 비활성화란?

서버에서 HTML을 미리 만들어서 브라우저에 보내주는 방식 → 서버가 HTML을 만들어서 보내기 때문에 브라우저는 JS실행이 끝나기 전에도 화면의 내용을 볼 수 있음

- 버튼 클릭같은 React의 상호작용 → 하이드레이션(Hydration) 과정 필요
  - 하이드레이션 : 서버에서 만든 HTML에 React가 이벤트 처리 등 상호작용 기능을 연결하는 과정

!image.png

- CSR (Client-Side Rendering)
  - 일반적인 React SPA에서 많이 사용하는 방식
  - 브라우저가 JS를 실행해서 화면을 만듦
  !image.png

| 구분      | CSR            | SSR                   |
| --------- | -------------- | --------------------- |
| HTML 생성 | 브라우저       | 서버                  |
| 초기 화면 | JS 실행에 의존 | HTML을 먼저 표시 가능 |
| SEO       | 추가 고려 필요 | 콘텐츠 노출에 유리    |
| 대표 사례 | React SPA      | Next.js               |

- SEO (Search Engine Optimization) : 검색 엔진 최적화
  - 사이트가 구글이나 네이버 검색 결과에 잘 노출되도록 만드는 작업
  - CSR과 SSR는 SEO에 무슨 관계가 있지?
    - CSR은 브라우저에서 JavaScript를 실행해 콘텐츠를 렌더링하기 때문에 처음 받은 HTML에 실제 콘텐츠가 거의 없을 수 있음. 따라서 검색 엔진이 콘텐츠를 확인하려면 JS를 실행해야 내용을 확인할 수 있음.
    - SSR은 서버에서 콘텐츠가 포함된 HTML을 생성해 브라우저에 전달하기 때문에 검색 엔진이 JavaScript를 실행하지 않아도 페이지 내용을 파악하기 더 쉬움.
- 단, 앱 라우터에서는 이 패턴을 서버 컴포넌트에서 사용하면 빌드 에러가 발생하므로 → 반드시 'use clinet' 지시문이 있는 클라이언트 컴포넌트 파일 안에서 선언해야 함
  - Next.js의 App Router에서는 컴포넌트를 크게 두 종류로 나눔
  | 구분              | 서버 컴포넌트     | 클라이언트 컴포넌트 |
  | ----------------- | ----------------- | ------------------- |
  | 주로 어디서 실행? | 서버              | 브라우저 중심       |
  | 기본 설정         | `use client` 없음 | `use client` 있음   |
  | `useState`        | 사용 불가         | 사용 가능           |
  | 클릭 이벤트       | 직접 처리 불가    | 처리 가능           |
  - Next.js의 app 폴더 안에 있는 컴포넌트 → 기본적으로 서버 컴포넌트
  ```jsx
  // 서버 컴포넌트
  // app/page.jsx

  export default function Home() {
    return <h1>안녕하세요!</h1>;
  }
  ```
  ```jsx
  // 클라이언트 컴포넌트
  "use client";

  import { useState } from "react";

  export default function Counter() {
    const [count, setCount] = useState(0);

    return <button onClick={() => setCount(count + 1)}>{count}</button>;
  }
  ```
- 왜 교재에서 빌드 에러가 발생한다고 했을까?
  ```jsx
  import dynamic from "next/dynamic";

  const Chart = dynamic(() => import("../components/Chart"), {
    loading: () => <div>차트 로딩 중...</div>,
    ssr: false,
  });
  ```

  - `ssr: false`
    : Chart 컴포넌트는 서버에서 렌더링하지 말고 브라우저에서 렌더링해
    - 이 코드를 서버 컴포넌트에서 직접 선언하면?
      - 서버 컴포넌트 : 서버에서 렌더링하는 컴포넌트
      - `ssr: false` : 이 컴포넌트의 서버 렌더링을 비활성화하라는 옵션
      - Next.js App Router에서는 서버 컴포넌트 안에서 dynamic()에 `ssr: false` 를 지정하는 걸 허용하지 않음 → 빌드 에러 발생
- 그렇다면 어떻게 해결할 수 있을까?
  - `‘use client’`가 있는 별도의 파일로 옮기면 됨
  ```jsx
  app / page.jsx; // 서버 컴포넌트
  ClientChart.jsx; // 클라이언트 컴포넌트
  ```
  ```jsx
  // page.jsx
  import ClientChart from "./ClientChart";

  export default function Page() {
    return (
      <main>
        <h1>대시보드</h1>
        <ClientChart />
      </main>
    );
  }
  ```
  ```jsx
  // ClientChart.jsx
  "use client";

  import dynamic from "next/dynamic";

  const Chart = dynamic(() => import("../components/Chart"), {
    loading: () => <div>차트 로딩 중...</div>,
    ssr: false,
  });

  export default function ClientChart() {
    return <Chart />;
  }
  ```
  ⇒ page.jsx는 서버 컴포넌트로 유지하면서 Chart만 브라우저에서 렌더링할 수 있음
- 주의할 점
  - dynamic() 자체가 서버 컴포넌트에서 무조건 금지된 게 아님
  - ssr: false 옵션이 빌드 에러의 핵심 원인임

### Vue Router에서는?

```jsx
import { createRouter, createWebHistory } from "vue-router";

const routes = [
  {
    path: "/",
    component: () => import("./views/Home.vue"),
  },
  {
    path: "/dashboard",
    component: () => import("./views/Dashboard.vue"),
  },
  {
    path: "/settings",
    component: () => import("./views/Settings.vue"),
  },
];

const router = createRouter({
  history: createWebHistory(),
  routes,
});
```

- `() ⇒ import(…)` : 비동기 라우트 로딩
- `const router = createRouter({ history: createWebHistory(), routes, });`
  - `createRouter()` : 라우터를 생성하는 함수
  - `history: createWebHistory()` : 브라우저 주소창에 /dashboard처럼 일반적인 URL을 사용하고 페이지 이동 기록도 관리하도록 설정함
  - `routes` : 작성한 URL과 컴포넌트의 연결 목록을 전달함

> 라우터를 하나 만들어. URL과 페이지의 연결 정보는 routes에 있고, 브라우저 주소와 이동 기록은 createWebHistory() 방식으로 관리해.

#### React와 비교

| React Router              | Vue Router                                |
| ------------------------- | ----------------------------------------- |
| `lazy(() => import(...))` | `() => import(...)`                       |
| `element={<Home />}`      | `component: () => import(...)`            |
| `Suspense`로 로딩 UI 처리 | Vue Router의 비동기 라우트 로딩 방식 사용 |

두 방식 모두 공통적으로 동적 `import()`를 이용해서 페이지 코드를 필요할 때 불러온다는 원리 사용

### 라우트 기반 분할의 장점

사용자 행동과 코드 경계가 일치함

### 주의할 점

1. 내비게이션 바나 사이드바 같은 공통 컴포넌트는분할하지 않아야 한다.
2. 첫 페이지(랜딩 페이지)는 가능한 한 가볍게 유지해야 한다.
3. 중첩된 라우트의 경우 부모-자식 관계를 고려해야 한다.

   ex.) /dashboard와 /dashboard/analytics가 있을 때, analytics가 dashboard의 공통 레이아웃을 사용하는지 확인해야함.
   - 공통 레이아웃은 부모 라우트에 포함하고, 실제 콘텐츠만 자식 라우트로 분리하는 것이 효율적

## 컴포넌트 레벨 지연 로딩

### 1) 모달과 다이얼로그 지연 로딩

- 다이얼로그 : 사용자와 정보를 주고받기 위해 화면에 나타나는 ‘대화 상자’의 포괄적인 상위 개념
  - 모달 다이얼로그 ： 뒤쪽 화면을 차단하는 방식
  - 모달리스 다이얼로그 ：다이얼로그가 떠 있어도 뒤쪽 화면을 자유롭게 조작할 수 있는 방식
- 모달 : 다이얼로그의 ‘작동 방식(특성)’ 중 하나로, 부모창 위에 레이어를 띄우고 사용자의 다른 모든 동작을 차단(Lock)하는 형태
  - 사용자가 버튼을 클릭하기 전까지는 화면에 나타나지 않으므로 초기 번들에 포함할 필요가 없음

### 2) 탭과 아코디언 컴포넌트

- 아코디언 컴포넌트 : 제목을 클릭하면 숨겨진 내용이 펼쳐지고, 다시 클릭하면 접히는 ui 컴포넌트

### 3) 조건부 기능과 권한 기능 로딩

- 조건부 기능 로딩 : 특정 조건을 만족할 때만 기능을 불러오는 것
- 권한 기반 로딩 : 사용자의 권한에 따라 필요한 기능만 불러오는 것

### 4) 무거운 라이브러리를 포함한 컴포넌트

### 5) 뷰포트 기반 지연 로딩

- `useRef` : 특정 DOM 요소를 기억하고 접근할 때 사용할 수 있는 React Hook
  ```jsx
  const footerTrigger = useRef(null);

  -> 실행하면 React가 이런 형태의 객체를 만듦
  footerTrigger = {
  	current: null
  };
  ```
- `useEffect` : React 컴포넌트가 렌더링된 뒤 특정 작업을 수행할 때 사용하는 Hook
  - 브라우저의 실제 DOM 요소를 관찰해야 하니까 useEffect 안에서 관찰자를 생성함
- `IntersectionObserver` : 특정 HTML 요소가 화면에 들어왔는지 감시하는 브라우저 API
  - `isIntersecting` : 관찰 대상이 설정한 관찰 영역과 교차하는지 나타내는 값
  - `entries` : 관찰 결과들의 배열
- `rootMargin: '100px'` : 기본 뷰포트의 관찰 영역을 상하좌우로 100px 확장
  - 푸터가 실제 화면에 보이기 약 100px 전부터 로딩 시작
- `observer.disconnect()` : 관찰 중단
  - 이미 푸터를 로딩하기로 결정 → 더 이상 스크롤 위치를 관찰할 필요가 없음
- `return () ⇒ observer.disconnect()` : useEffect의 클린업(cleanup)함수
  - 컴포넌트가 언마운트되거나 Effect가 정리될 때 관찰을 해제함
  - 불필요한 관찰이 계속 남지 않도록 하는 역할

## 잘못된 분할 지점과 안티패턴

### 너무 작은 청크 남발

- 모든 컴포넌트를 분할하는 것
- 작은 컴포넌트를 무분별하게 분할 → HTTP 요청 오버헤드가 실제 코드 크기보다 커짐 ⇒ 성능 저하
  - 오버헤드 : 실제 작업 외에 추가로 드는 비용
- HTTP/2 멀티플렉싱이 하나의 연결로 여러 요청을 병렬 처리하지만, 각 청크를 로드하는 오버헤드(번들러 런타임 코드, 파싱 비용)가 실제 코드 크기보다 클 수 있음
  - HTTP : 브라우저와 서버가 데이터를 주고받을 때 사용하는 통신 규칙
  - HTTP/2 멀티 플렉싱 : 하나의 연결을 통해 여러 요청과 응답을 동시에 진행할 수 있도록 하는 기술
  !image.png
- 업계에서는 경험적으로 최소 20~30KB 이상의 코드만 별도 청크로 분리하는 것 권장

### 첫 화면 렌더링에 필수적인 컴포넌트 지연 로딩

- 페이지를 열자마자 보게 되는 첫 화면에 보이는 콘텐츠의 컴포넌트는 지연 로딩하면 안됨
- 초기 로딩은 빨라지지만 화면이 비어 보이는 시간이 늘어나 오히려 사용자 경험이 나빠짐

### 공통 모듈을 여러 청크에 중복 포함

- 여러 페이지에서 사용하는 공통 모듈을 각 청크에 중복 포함하면 → 사용자는 같은 코드를 여러 번 다운로드하게 됨

### 모든 라우트를 무분별하게 분할

- 라우트 기반 스플리팅이 효과적이라고 해서 모든 페이지를 개별 청크로 분할하는 것은 아닝ㅁ
- 크기가 작은 정보성 페이지들은 하나의 청크로 묶는 것이 HTTP 요청 수를 줄이는 데 유리

### 사용자 인터랙션에 필수적인 컴포넌트 지연 로딩

- 결제, 로그인, 폼 제출 같은 핵심 기능을 사용자가 버튼을 클릭한 후에 로드 → 치명적인 UX 문제가 발생 ⇒ 사용자는 버튼을 눌렀는데 아무 일도 일어나지 않는 것처럼 느끼고, 로딩 중인지조차 알 수 없음
- 사용자가 ‘결제 진행’ 버튼을 클릭했는데 로딩 인디케이터를 보게 되면 전환율(conversion rate)이 떨어질 수 있음
  - 전환율 : 원하는 행동을 완료한 사용자의 비율
- 중요한 사용자 흐름에서는 지연이 허용되지 않음
