# 10.4 지연 로딩의 UX 최적화

## 개요

코드 스플리팅을 도입하면 초기 로딩 성능은 개선되지만 새로운 UX 문제 발생

사용자가 특정 페이지나 기능에 접근할 때 청크를 다운로드하는 동안 빈 화면이 표시되거나, 네트워크 오류로 청크 로딩이 실패하면 애플리케이션이 깨짐

### 지연 로딩의 UX를 개선하려면 두 가지 상황을 잘 처리해야 함

1. 청크가 로딩되는 동안의 대기 상태
2. 청크 로딩이 실패하는 경우

→ 리액트는 이 두 상황을 위해 Suspense와 에러 바운더리(Error Boundary)를 제공

- Suspense : 청크 로딩 중 폴백 UI를 선언적으로 정의할 수 있게 함
- Error Boundary : 로딩 실패를 포착해 복구할 수 있게 함

## 서스펜스 폴백 전략과 로딩 상태 디자인

리액트의 lazy()로 컴포넌트를 동적으로 임포트할 때, 해당 청크가 다운로드되는 동안 리액트는 무엇을 렌더링해야 할지 모름 → Suspense 컴포넌트로 감싸면 로딩 중에 표시할 폴백 UI를 지정할 수 있음

### 세분화된 서스펜스 경계

- 첫 번째 개선 : 서스펜스 경계를 세분화하는 것
- 전체 앱을 하나로 감싸는 대신, 페이지나 기능 단위로 나눔 → 로딩 중인 부분만 폴백으로 바뀌고 나머지는 정상적으로 표시됨

```jsx
function App() {
	return (
		<div>
			<Header />
			<Sidebar />
			<main>
				<Routes>
					<Route
						path="/dashboard"
						element={
							<Suspense fallback={<DashboardSkeleton />}>
								<Dashboard />
							</Suspense>
						}
					/>
					...
```

### 스켈레톤 스크린 vs 스피너

- 스피너 : 구현이 간단하지만, 사용자가 무엇이 로딩되는지 예측하기 어려움
- 스켈레톤 스크린 : 실제 콘텐츠의 윤곽을 미리 보여주므로 사용자 경험이 더 좋음
  - 실제 컴포넌트와 최대한 비슷한 구조를 유지해야 함

### 지연된 폴백 표시

- 청크가 빠르게 로드되면(200ms 이하) 폴백을 보여주지 않는 것이 더 좋음
  - 폴백이 잠깐 나타났다 사라지면 깜빡임이 발생해 오히려 거슬림
- 하지만 단순히 지연 시간만 추가하면 새로운 문제가 발생함
  - 201ms에 로드가 완료되면 200ms 기다린 후 1ms만 폴백이 보임
  - 이를 방지하려면 → 폴백이 한 번 표시되면 최소 시간 동안 유지해야 함
- 가장 실용적인 방법 : CSS 트랜지션 활용
  - 폴백을 부드럽게 페이드 인/아웃하면 짧은 시간에도 자연스러움

### Transition API로 부드러운 전환

- 리액트 18의 useTransition을 사용하면 → 페이지 전환 시 현재 화면을 유지하면서 백그라운드에서 새 페이지를 로드할 수 있음
- 이전 페이지를 즉시 지우고 폴백을 보여주는 대신, 이전 페이지를 유지하다가 새 페이지가 준비되면 부드럽게 전환됨
- `useTransition` : React에서 일부 상태 업데이트를 긴급하지 않은 전환 작업으로 표시할 수 있게 해주는 Hook
  ```jsx
  import { useTransition } from "react";

  const [isPending, startTransition] = useTransition();
  ```

  - `isPending` : 전환 작업(Transition)이 진행 중인지 알려주는 값
  - `startTransition` : 상태 업데이트를 Transition으로 처리하도록 지정하는 함수

## 에러 바운더리로 청크 로딩 실패 처리하기

코드 스플리팅을 사용하면 청크 로딩이 실패하는 경우가 종종 발생함

- 가장 흔한 원인 : 새 배포
  - 사용자가 애플리케이션을 열어둔 상태에서 새 버전이 배포 → 이전 버전의 HTML은 더 이상 존재하지 않는 청크 파일을 참조함
  - 사용자가 새 페이지로 이동하려고 하면 404 에러가 발생하고, `‘ChunkLoadError: Loading chunk 3 failed’`같은 에러가 던져짐
- 에러를 처리하지 않으면 → 애플리케이션이 멈추고 빈 화면만 보임
- 리액트에서는 컴포넌트 렌더링 중 에러가 발생하면 전체 컴포넌트 트리가 언마운트됨
- 이를 방지하려면 → 에러 바운더리를 사용해서 에러를 포착하고 대체 UI를 보여줘야 함

### 기본 에러 바운더리 구현

리액트는 에러 바운더리를 위한 훅을 제공하지 않음 → 클래스 컴포넌트로 구현

- 기본적인 형태가 실무에서 필요한 두 가지 개선
  1. 청크 로딩 에러인지 다른 런타임 에러인지 구분해야 함
  2. 자동으로 재시도하는 매커니즘 필요

#### 함수형 컴포넌트 vs 클래스 컴포넌트

- 함수형 컴포넌트
  ```jsx
  import { useState } from "react";

  function Counter() {
    const [count, setCount] = useState(0);

    return <button onClick={() => setCount(count + 1)}>{count}</button>;
  }
  ```
- 클래스형 컴포넌트
  ```jsx
  import { Component } from "react";

  class Counter extends Component {
    constructor(props) {
      // 초기 설정 담당
      super(props);
      this.state = { count: 0 }; // 상태 저장
    }

    // 화면에 보여줄 JSX 반환
    render() {
      return (
        <button
          onClick={
            () => this.setState({ count: this.state.count + 1 }) // 상태 변경
          }
        >
          {this.state.count}
        </button>
      );
    }
  }
  ```

| 비교           | 함수형               | 클래스형                |
| -------------- | -------------------- | ----------------------- |
| 선언           | `function`           | `class`                 |
| 상태 관리      | `useState`           | `this.state`            |
| 상태 변경      | `setCount()`         | `this.setState()`       |
| 화면 반환      | `return`             | `render()`              |
| 생명주기 처리  | `useEffect` 등 Hooks | `componentDidMount` 등  |
| 현재 권장 방식 | 주로 사용            | 기존 코드에서 많이 접함 |

#### Q. ErrorBoundary는 왜 클래스형 컴포넌트로 만들었을까?

```jsx
class ErrorBoundary extends React.Component {
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    console.error(error);
  }
}
```

- React의 기본 에러 바운더리 기능은 다음과 같은 클래스 컴포넌트의 메서드를 사용함
  - `getDerivedStateFromError()` → 에러가 발생하면 상태를 변경
  - `componentDidCatch()` → 발생한 에러를 기록
- 함수형 컴포넌트에는 이 두 메서드에 직접 대응하는 기본 Hook이 없음 → React의 기본 기능만으로 ErrorBoundary를 직접 구현할 때는 클래스형 컴포넌트를 사용
- 다만 `react-error-boundary` 같은 라이브러리를 사용하면 → 함수형 컴포넌트에서도 에러 바운더리 활용 가능

### 청크 로딩 에러 감지와 자동 재시도

- 청크 로딩 에러 → ChunkLoadError 또는 Failed to fetch 메시지로 식별 가능
- 에러 발생 시 → 일정 시간 대기 후 다시 시도하거나, 사용자에게 새로고침을 안내함

### 동적 import에 재시도 로직 추가

- 에러 바운더리는 컴포넌트 렌더링 중 발생한 에러만 포착함
- lazy()의 동적 임포트 자체가 실패하면 → Promise 거부(rejection)가 발생하고 이것도 에러 바운더리로 전파됨
  - 더 견고한 방법 : 동적 임포트를 재시도 로직으로 감싸는 것

### 배포 중 청크 버전 불일치 처리

- 실무에서 가장 성가신 경우 : 사용자가 애플리케이션을 열어둔 상태에서 새 버전이 배포되는 것
- index.html은 이전 버전 ↔ 청크 파일은 새 버전으로 교체되어 해시가 맞지 않음
- 이를 방지하려면 → 배포 시 이전 청크를 일정 기간 보관하거나, 청크 로딩 실패 시 강제로 새로고침

### 페이지 단위 에러 바운더리 배치

- 전체 앱을 하나의 에러 바운더리로 감싸면 → 한 페이지의 에러가 전체 앱을 무너뜨림
- 대신 페이지나 주요 기능별로 에러 바운더리를 배치 → 에러의 영향 범위 제한
