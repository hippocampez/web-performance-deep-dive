# 11.1 클라이언트 중심 개발의 함정

## 개요

리액트, 뷰, 앵귤러 같은 현대적 프론트엔드 프레임워크 보편화 → 웹 개발의 중심이 서버에서 클라이언트로 이동함

## SPA가 가져온 번들 크기 폭발

### SPA (Single Page Application)

하나의 HTML 페이지를 기반으로, 페이지 전체를 새로고침하지 않고 필요한 부분만 동적으로 변경하는 웹 애플리케이션 방식

- 기존 웹사이트는 페이지를 이동할 때마다 서버에서 새로운 HTML 문서를 받아왔음. 반면 SPA는 처음에 HTML과 JavaScript를 로드한 뒤, JavaScript를 이용해 화면을 변경함.

| 구분        | 기존 MPA             | SPA                                 |
| ----------- | -------------------- | ----------------------------------- |
| 페이지 이동 | 새로운 HTML 요청     | JavaScript로 화면 변경              |
| 화면 렌더링 | 주로 서버 중심       | 주로 클라이언트 중심                |
| 초기 로딩   | 페이지별 리소스 로드 | 초기 JavaScript 부담이 커질 수 있음 |
| 페이지 전환 | 전체 페이지 새로고침 | 필요한 부분만 갱신                  |

#### SPA의 장점

필요한 부분만 동적으로 렌더링 → 빠르고 부드러운 사용자 경험 제공

#### SPA의 단점

클라이언트 측에서 라우팅, 상태 관리, 렌더링 로직 모두 담당해야 함 → 번들 크기가 폭발함

### SPA가 발전하면서 새로운 성능 문제 발생 : 번들 크기 폭발

#### 번들(Bundle)이란?

웹 애플리케이션에서 사용하는 여러 JavaScript 모듈과 라이브러리를 빌드 도구가 묶어 생성한 파일 또는 파일들의 집합

#### 번들 크기 폭발이 발생하는 이유

SPA의 기능이 많아질수록 필요한 JavaScript코드도 증가함.

특히 모든 페이지의 코드를 하나의 초기 번들에 포함하면, 사용자가 당장 방문하지 않는 페이지의 코드까지 다운로드해야 할 수 있음.

- 번들 크기 폭발 : 애플리케이션 규모가 커질수록 초기 JavaScript 번들이 비대해지는 현상
- 단, SPA라고 해서 반드시 모든 코드를 한 번에 다운로드하는 것은 아님. 코드 스플리팅을 적용하면 필요한 코드만 나누어 로드할 수 있음.

### 번들 크기 증가가 성능에 미치는 영향

JavaScript 번들이 커지면 단순히 다운로드 시간만 증가하는 것이 아님.

#### 번들 크기가 증가하면 다음과 같은 문제 발생

- 초기 로딩 지연 : JavaScript 다운로드에 더 많은 시간 필요
- 파싱 및 실행 비용 증가 : 브라우저가 처리해야 할 코드가 많아짐
- 메인 스레드 점유 : JavaScript 실행이 길어지면 화면 업데이트와 사용자 입력 처리가 지연될 수 있음
- 저사양 기기에서 성능 저하

## 클라이언트에서 모든 것을 처리하려는 시도의 문제

JavaScript 엔진의 성능 향상과 프레임워크의 발전으로 클라이언트 측에서 처리할 수 있는 기능이 점차 늘어나면서 많은 로직이 서버에서 클라이언트로 옮겨옴

서버는 단순히 JSON API만 제공하고, 나머지 모든 로직은 클라이언트에서 처리하는 구조가 일반화됨

### 클라이언트 중심 처리 방식의 문제

SPA는 페이지 전환과 사용자 상호작용을 JavaScript로 처리하면서 풍부한 사용자 경험을 제공함.

하지만 애플리케이션이 복잡해질수록 서버에서 처리하는 것이 더 적합한 작업까지 클라이언트에서 처리하려는 문제 발생

#### 클라이언트가 너무 많은 작업을 담당할 때 발생하는 문제

- JavaScript 번들 크기 증가
- CPU 사용량 증가
- 메인 스레드 블로킹
- 기기별 성능 차이

⇒ 모든 작업을 클라이언트에서 처리하기보다는 서버와 클라이언트의 역할을 적절히 분리하는 것이 중요

## 서버와 클라이언트의 최적 역할 분담 기준

Q. 어떤 로직을 서버에서 처리하고, 어떤 로직을 클라이언트에서 처리해야 할까?

### 클라이언트에서 처리해야 할 것

사용자와 직접 상호작용하는 부분에 집중해야 함 → 즉각적인 피드백이 필요하거나 사용자 입력에 따라 UI가 동적으로 변해야 하는 경우

- UI 상태 관리 : 모달 열림/닫힘, 탭 전환, 아코디언 확장/축소
- 입력 중 즉각 피드백 : 타이핑하는 동안의 문자 수 표시, 실시간 자동완성
- 클라이언트 전용 로직 : 드래그 앤드 드롭, 캔버스 조작 같이 브라우저 API를 활용하는 기능
- 오프라인 기능 : 서비스 워커를 활용한 오프라인 지원, 로컬 캐싱
  - 서비스 워커 : 브라우저의 백그라운드에서 동작하며 네트워크 요청 제어와 캐싱 등을 지원하는 JavaScript 실행 환경
  - 로컬 캐싱 : 데이터를 사용자 기기에 저장하여 다시 사용할 때 불필요한 요청을 줄이는 방식

### 서버에서 처리해야 할 것

데이터 처리, 비즈니스 로직, 보안이 중요한 작업은 서버에서 처리 → 클라이언트 번들을 가볍게 유지하고, 서버의 강력한 연산 능력 활용 가능

- 데이터 필터링 및 정렬 : 큰 데이터셋의 검색, 필터링, 정렬, 페이지네이션
  - 페이지네이션 : 전체 데이터를 일정한 크기의 페이지로 나누어 제공하는 방식
- 복잡한 계산 : 할인 계산, 통계 집계, 데이터 분석
- 비즈니스 규칙 검증 : 재고 확인, 쿠폰 유효성 검증, 권한 체크
- 데이터 가공 : 날짜 포매팅, 텍스트 변환, 이미지 리사이징
- 보안 관련 로직 : 인증, 권한 부여, 민감한 데이터 처리

### 실용적인 의사결정 기준도 필요

1. 이 로직이 없어도 사용자가 콘텐츠를 볼 수 있는가?
   - 상품 목록을 표시하는 데 필수적인 로직이라면 서버에서 처리해서 SSR로 제공하는것이 좋다.
2. 이 로직을 클라이언트에서 처리하면 얼마나 많은 코드가 추가되는가?
   - 10KB 미만의 작은 유틸리티라면 클라이언트에 포함해도 괜찮지만, 50KB 이상의 무거운 라이브러리가 필요하다면 서버 처리 고려해야 한다.
3. 이 로직은 즉각적인 응답이 필요한가?
   - 사용자가 타이핑하는 동안 실시간으로 반응해야 한다면 클라이언트에서 처리해야 한다.
4. 이 로직은 보안이 중요한가?
   - 가격 계산, 할인 적용, 권한 검증 같은 로직은 반드시 서버에서 처리해야 함
